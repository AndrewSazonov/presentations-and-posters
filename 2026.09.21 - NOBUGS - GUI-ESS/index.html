One facility, two host countries

ESS is in Lund. DMSC is in Lyngby, near Copenhagen.

Worth ten seconds, not more. The neutron source and its instruments are in Lund; the data management and software centre is in Copenhagen, on the other side of the bridge and in another country. Most of the software in this talk is written on one side of that water and used on the other. It is not the reason the GUI work is fragmented — that is on the challenges slide, and it is organisational — but it is the backdrop to it.

Qt is the one thing the desktop side agrees on, and it is agreement by accident rather than by policy: three groups reached for it independently. On the web, four projects and four stacks, none of them sharing a component with another. Worth saying out loud about the last two: ESS did not inherit either of them. It started User Office in 2018 and it leads SciCat today. Two projects we began ourselves, and they still landed on different frameworks — Angular for one, React for the other. The web stack itself was not the free choice it looks like: both serve people who are not at the facility, and a desktop application would have to be installed by every one of them.

Suggests a scattering model from the data

Answers questions about the fit

Sets parameters and runs the fit when asked

Its tools are off until you switch them on

Cut from the slide, still worth saying. UI GENERATION: essreduce already declares its reduction parameters with types, which is exactly what a generator would read — that is why this is a smaller job than it sounds, the declarative half being already solved for other reasons. The notebooks we have are the pattern, one per experiment. For a NEW project the starting material is different and better: a library of shared QML widgets plus four or five applications already assembled from them, which is the kind of worked corpus an assistant can actually build against. Nothing here is running yet. AI: built-in heuristics take over when there is no API key; it reaches the fitting engine over MCP. Eleven tools, and the split between them is the design decision worth defending. Four only read — list the models, describe a model's parameters, report the current state, report the fit results. The other seven write: set the model, set a parameter, set several, set the Q range, enable polydispersity, add or remove a structure factor, and run the fit. Every one of those seven is behind a switch in the sidebar that is OFF until somebody turns it on, and answers "AI tools are disabled" until they do. So the assistant is read-only by default and capable on request, which is the right way round: a scientist has to be able to say where every number in a published refinement came from. Next is the same idea inside the EasyScience GUIs, starting with explaining a fit. AI coding assistants are routine in development; the only one we ship is this one.
