Where analysis sits

Acquisition

run the experiment, write raw events

Reduction

correct, bin, turn events into a pattern

Analysis

fit a model, extract the science

SasView
+ many technique-specific tools

The point of the slide is only to place the talk: everything that follows is about the last box. 1.4The problem

The same work starts again

A new technique gets a new program

A new program gets a new interface

Every usability lesson is learned once, then lost

Different science. Same interface rebuilt every time.

This is the hinge of the talk. The rest is: we built one interface carefully, then made it reusable so the next technique does not start from an empty window.

2.3Design evolution

The interface came before the science

The usual order

code→interface

The interface takes its shape from the code.

Ours

interface→code

The interface can be thrown away and redrawn.

Techniques that share the workflow share the interface.

This is the slide that earns the next section. Designing for the WORKFLOW rather than for one technique's code is what left us with an interface that any technique sharing that workflow can wear — which is the whole unification claim, and the talk's title. The left panel dims on the second click on purpose: the point is not that the usual order is wrong, it is that it is the one everybody else is still in. Say the two arrows out loud. The mechanism, if anyone asks, is in the backup deck: QML describes a screen as layout and state rather than drawing it, the frontend meets a Python backend at a thin boundary so the science can be stubbed or arrive late, and Live Preview puts an edit into the running application without a rebuild. None of that is the point on this slide — the point is the ORDER, and what it costs to change your mind. Do not call QML "no-code": it is a declarative UI language, which is not the same claim.

3.6UX principles

Three ways to run the same workflow

GUIclick through the workflow

CLIthe same project, one command

Librarythe same objects, in Python

Same objects, same order, in all three.

The claim is continuity: moving from the application to a terminal to a notebook is not a change of mental model, only a change of how much you type. Worth saying that the CLI is not a separate tool — `python -m easydiffraction PROJECT fit` refines the very project directory the GUI saved, and writes the results back into it. Same objects, same order, literally.
