Challenges, and the controls split

More organisational than technical. Beamline controls are (mostly) under our scope; accelerator controls are not.

Organisational
  • Each group picks its own stack, so little is shared
  • GUI expertise stays inside teams; no common review or style practice
  • GUI work competes with science deliverables for the same people
Technical
  • Scientific plotting is rarely QML-native, so embedding it is extra work & can break styling
  • What is QML-native is general-purpose charting, not enough for scattering data
  • NICOS ESS fork, merging back after alignment of expectation
Accelerator vs beamline
  • ECDC sits inside Science and runs the same NICOS client on every instrument, so one approach rather than one per beamline
  • Low level EPICS controls sit in Accelerator division; we share no UI stack with them

UI generation and AI assistants

The assistant ships today; UI generation is not built yet.

UI generation
  • Not used today, but essreduce already declares reduction parameters with types — what a generator would read
  • Generate a reduction notebook per experiment, then a Voilà GUI from it, using the notebooks we have as the pattern
  • The same for the EasyScience libraries, generated from the data analysis notebooks
  • A new EasyScience project could be built this way from the start, with our apps & prototypes as the reference
AI assistants
  • SANS-webapp — SANS fitting with the assistant built in, on PyPI today
  • Claude suggests a scattering model from the data; built-in heuristics take over with no API key
  • Reaches the fitting engine over MCP, read-only: it advises but does not change the fit
  • Next: the same idea inside the EasyScience GUIs, starting with explaining a fit
  • AI coding assistants are routine in development; the only one we ship is above
